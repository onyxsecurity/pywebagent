# WHAT THE GATE FOUND (round 22, G15): the shipped Azure lane's session alert producer failed on EVERY
# send — 65 swallowed "failed to publish one session alert-processing request (continuing)", and the
# alert-processing queue empty after every drive — while the pod stayed healthy. That is the ticket's own
# footgun-2 shape on a new path, so it was fixed rather than ledgered.
#
# THERE WERE TWO CAUSES, and the first was hiding the second.

=== CAUSE 1 — one ServiceBusSender shared across concurrent tasks (a real coroutine-safety bug)
    common_core/services/queue/asb.py creates ONE sender at connect() and the ingestion service shares
    one client across every object-processing task. ServiceBusSender is not coroutine-safe: overlapping
    send_messages calls race on the single AMQP link and the loser sees a half-open handler.
    Symptom, verbatim from the pre-fix pod:
        AttributeError("'NoneType' object has no attribute 'create_sender_link'")
    THE FIX: serialise sends on the shared link (asyncio.Lock in send_message). The receive side already
    solves the same hazard the other way — the consumer pool gives each worker its OWN client
    (consumer_pool.py factory mode) — but sends are small and infrequent next to ingest, so a lock costs
    less than a link per message. Regression tests: tests/common_core/services/test_asb_sender_concurrency.py
    (20 concurrent sends must all land, and never overlap inside the sender).

=== CAUSE 2 — the identity had no Send grant on the alert queue (an infrastructure gap)
    With the crashes gone, the real error was legible underneath them:
        AMQPLinkError: Error condition: amqp:unauthorized-access
        Error Description: Unauthorized access. 'Send' claim(s) are required to perform this operation.
    The Azure workload identity was granted exactly two roles — Data Receiver on ITS OWN ingestion queue
    and Blob Data Reader on the storage account (cell-azure-instance/workload_identity.tf) — while the
    sessions step publishes to the alert-processing queue, as the AWS lane does through its IRSA policy.
    So the lane as authored could never publish an alert on Azure.
    THE FIX: a queue-scoped `Azure Service Bus Data Sender` role assignment on the alert-processing queue
    for that identity, in onyxsecurity/infrastructure#1575 — scoped to the one queue, not the namespace.
