The claim: a handler exception calls abandon_message, which on Service Bus re-offers the message
IMMEDIATELY and increments its delivery count, so a transient dependency failure cycles
receive -> fail -> abandon at full speed and exhausts max_delivery_count, parking good work in the
dead-letter sub-queue. The AWS lane has no such shape (abandon is a no-op; the message is invisible
for its 600s visibility timeout).

CONFIRMED, and this run's own evidence contains the proof: at6-05 section J shows
  Abandoned message for redelivery   18:35:05.626Z
  redelivered queue message ... receive_count=2   18:35:05.647Z
21 ms apart. It only stopped there because the induced lock was released after one cycle.

The fix, and why it is shaped this way: abandon_message now RETURNS whether the release is immediate
(ASB True, SQS False), and the pool sleeps error_backoff_seconds only in the immediate case. Sleeping
on the SQS path would idle a worker whose message is invisible anyway, so the AWS lane is unchanged.
Tests: TestHandlerErrorBackoff in tests/common/services/queue/test_consumer_pool.py — both directions,
each hard-capping its polls so a regression fails fast instead of spinning the suite.

THE STRUCTURAL HALF WAS RIGHT, AND IS FIXED (dfe23b9e83). Correctness rested entirely on
lock_renewal_interval_seconds < lock_duration — a relationship maintained by convention across two
repositories and enforced nowhere — with the loop sleeping the full interval BEFORE its first renew.
Setting the two equal reads as reasonable ("renew every five minutes on a five-minute lock") and puts
the first renewal exactly at expiry, with precisely the consequence the reviewer describes.
The delay is now derived from the message's own locked_until_utc: half the remaining lock, so renewal
lands at least twice per lock period whatever the queue is configured with, falling back to the
configured interval when the broker gives no deadline.
