# WHAT WAS WRONG. at7's ui_proof_steps step 2 asks for each class located IN THE LIST (/ai-assets). That
# was not obtainable on this box: the list is served from the asset_inventory READ MODEL
# (applications-table/index.tsx:166-173), and that projection had been frozen since 2026-08-18 19:42Z —
# 157 rows, while live assets had 316. Every asset this run produced was invisible to the browsable list,
# and earlier rounds proved the classes only by deep-linking to the detail routes, which is not what the
# step asks for. A broken component never softens the bar, so it was fixed rather than worked around.
#
# ROOT CAUSE, measured not guessed. Two faults, one behind the other:
#   1. NOTHING WAS POLLING THE python-worker TASK QUEUE. `tctl taskqueue describe --taskqueue python-worker`
#      returned an EMPTY poller table. The temporal-python-worker pod was 1/1 Running, 33 h old, 0
#      restarts — but its log ends at 2026-08-19T12:12:30Z with a Postgres ConnectionRefusedError followed
#      by its own clean "Shutting down worker..." / "Worker shut down complete". The worker had exited its
#      run loop while the container stayed alive, so Kubernetes saw a healthy pod polling nothing. This is
#      exactly the "a READY pod can silently fail" case the stack-health skill exists to catch.
#   2. THE FRESHNESS SCHEDULE HAD A WEDGED EXECUTION. asset-inventory-freshness-schedule (interval 20s)
#      held RunningWorkflows = [asset-inventory-freshness-schedule-execution-2026-08-19T09:05:20Z] with
#      LastRunTime 1 day ago — it could never complete with no poller, and the schedule will not start a
#      new run while one is outstanding.

## 1. THE FIX — two actions, both on the env, none on the product
    a) kubectl -n onyxd rollout restart deploy/temporal-python-worker
    b) tctl workflow terminate --wid asset-inventory-freshness-schedule-execution-2026-08-19T09:05:20Z
