This ticket's **Mechanism** section describes the frozen base `67b4096f`. Upstream `main` has since changed
that path, and PRDCT-11935's branch now carries those commits, so three of this ticket's statements are out
of date while the defect itself is not. Correcting the record rather than editing the ticket body.

**1. What changed upstream.** Three `main` commits, all merged into PRDCT-11935's branch (each verified an
ancestor of that branch head `2b60fdc4df25188104e737e6311087681355eff8`):

- `ac7f9de777` — *PRDCT-12048 | Make issue relief statements insert-only and diff-guarded*
- `d7ae29286a` — *PRDCT-12067 | Make issue-detection instance writes resilient to concurrent duplicate work*
- `366ab0c488` — *PRDCT-12048 | Split the governance persist and baseline the issue write counters*

Together they make the instance-write path **diff-guarded and counted**. The guard is at
`common/repository/issues/issue_repository.py:1316-1329`: `evidence_differs` is an `IS DISTINCT FROM` over
the five stored evidence columns, `has_evidence_write = has_any_incoming_evidence & evidence_differs`, and
the UPDATE's WHERE (`should_reopen_or_refresh`) — in the code's own comment — *"Skip rows that are already
OPEN with nothing new to write, and never touch IGNORED rows."*

**2. The per-scan `updated_at` re-touch this ticket documents no longer occurs for byte-identical evidence.**
The Mechanism section says the refresh-already-open branch *"rewrites the evidence columns and bumps
`updated_at`"* on *"every re-evaluation that still MATCHES — even against byte-identical stale findings"*.
That was true of the base; it is not true at head. Measured on an identity-pinned worker across **three
consecutive covered post-removal scans** of a removed skill: its seven `issue_instances` (6721, 6722, 6725,
6726, 6729, 6732, 6733) stayed **byte-frozen** — `updated_at` equal to `created_at`
(`2026-08-24 01:44:50.117728+00`), all five evidence columns unchanged by md5, and
`asset_posture_findings.classified_at` frozen at `01:44:48.829425+00` — while the tenant's
`outcome="unchanged"` write counter rose **126,744 → 170,920**. The no-op is now counted rather than
invisible. (The Mechanism section's line cites — `:1167`, `:1184-1190`, `:1224-1229`, `:1277` — are
frozen-base numbers and no longer resolve to what the text describes.)

**3. Open question (a) is therefore partially implemented upstream.** This ticket asks *"whether the
evidence-refresh loop (re-writing Evidence from cached findings on every re-affirm) should be tempered"*.
Upstream has tempered exactly the write half: a re-affirm against byte-identical evidence performs no write
and bumps nothing. What (a) still leaves open is the rest of the loop — the re-evaluation itself still runs
every scan, and nothing surfaces that the underlying finding is stale.

**4. The defect this ticket is about is measured UNCHANGED on head.** All four halves still hold:

- **Open forever** — the instances stay `IssueInstanceResolveStateOpen` with `closed_at NULL` after the
  source artifact is really removed.
- **Deleted content as live Evidence** — `/posture-issues` still renders the deleted file's own line verbatim
  as live Evidence on an Open issue (captured this round).
- **No close-on-absence** — nothing closes them; the only absence-adjacent close hook is gated on
  `assets.is_deleted`, which no scanner-lane writer sets (the shared root cause with PRDCT-12069).
- **No staleness surfacing** — `classified_at` is still rendered nowhere.

So the diff-guard changes *how often the row is written*, not *what the product shows a user*. Open
questions (b) and (c) are untouched by it.
