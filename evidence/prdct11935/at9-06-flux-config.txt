## 3. WHAT THIS MEANS — the publish is CONDITIONAL, and the gate does NOT fail the render
=========================================================================================================
## The publish is gated on
##     var.create_service_bus && var.create_endpoint_asset_ingestion_queue          (fluxcd_config.tf:113)
## because both values are read off the real resources, so they are 'published only when those
## resources exist'.
##
## What the gate does NOT do is fail the render. Flux resolves an unprovided ${...} to the EMPTY
## STRING and the Kustomization reconciles successfully. So an instance whose flux release enables the
## lane while the queue toggle is off gets an EMPTY queue name, and the failure surfaces at the POD —
## the transport guard refuses to start, which is a CrashLoopBackOff. That is exactly why the apply
## ORDER is load-bearing: infrastructure first, then the flux toggle. The module comment quoted in §1
## says so in the same words, and the release.yaml comment matches (at8-04).

## The load-bearing property d-b5 needs: the lane binds to its OWN keys, not the shared
## servicebus_namespace the extension consumers use —
      endpoint_asset_ingestion_servicebus_namespace   (the lane's own, :115)
   vs servicebus_namespace                            (the shared key, used by the extension lanes)
   and the comment gives the reason: the shared key is published only with create_ingestion_queue, so
   reusing it would make this lane silently depend on the EXTENSION lane's toggle.
