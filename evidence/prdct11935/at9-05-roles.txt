## 3. WHY THE SENDER EXISTS — the code path, traced at this head, not asserted
##      service.py:156   the Azure branch constructs the alert producer, gated on the queue being
##                       configured: `if config.cloud is CloudProvider.AZURE and config.alert_processing_asb.queue_name:`
##      service.py:169   and warns + leaves it None when it is not

##      asb.py:183       `await sender.send_messages(msg)` — the actual AMQP send, which is what needs the
##                       'Send' claim
##    The lane's own shipped config sets that queue (flux-fleet .../saas/onyx-app/release.yaml alert_processing_asb),
##    so this is a live path on both Azure instances, not a dormant one.

## 4. WHAT DROPPING IT WOULD COST — and why "additive" does not mean "optional"
##    Without the Sender claim the send raises `amqp:unauthorized-access — 'Send' claim(s) are required`.
##    That failure is caught PER REQUEST at sessions_writer.py:112 (`failed += 1`), never propagates, and
##    the object still ACKs at message_handler.py:124 — no redelivery, no dead-letter. Inventory and
##    posture writes all succeed, so the pod stays green while every session alert is lost permanently.
##    The only signal is one counter: `session_alerts{outcome="publish_failed"}` at writers.py:688 — and
##    THAT counter exists only because this PR added it. This run has already seen the exact shape: the
##    round-24 leg found 65 swallowed publish failures with an empty alert queue and no metric moving at
##    all, which is what the head commit fixes.

## 5. PRECEDENT — this is AWS parity, not a new privilege

##    the AWS policy (which also carries a redundant duplicate SendMessage statement at :32 — a
