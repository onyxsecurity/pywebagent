================ G. why an app registration was NOT available (identity choice) =========
The brief asked for a dedicated app registration / service principal with its secret in a k8s secret.
That path is closed in this tenant and the closure is mechanical, not a preference:

  $ az ad app create --display-name prdct11935-at9lp-consumer --sign-in-audience AzureADMyOrg
  ERROR: Insufficient privileges to complete the operation.
      (coder-agent-app is Global Reader + subscription Owner, but holds no
       Application.ReadWrite.OwnedBy — it cannot create directory objects.)

  $ curl .../v1.0/policies/authorizationPolicy      -> http 403 Authorization_RequestDenied
      (cannot even read whether member users may register apps)

  Interactive fallback as coder-agent@onyx.security (az login --use-device-code) was driven twice in a
  real browser through the JumpCloud SAML front door and failed deterministically at the same wall
  both times — this is the documented AADSTS5000811 federation defect, not a transient:

      AADSTS5000811: Unable to verify token signature. The signing key identifier does not match any
      valid registered keys.
      Request Id: 082c28e2-7865-46fd-a95d-00dff9c9c800   (attempt 1, 2026-08-24T00:36:16Z)
      Trace/Request Id: aeb821…                          (attempt 2, ~2026-08-24T00:45Z)

So the runtime identity used is a USER-ASSIGNED MANAGED IDENTITY instead — which is strictly BETTER
for this AT, on three counts:
  1. it is the SAME identity type the terraform authors (azurerm_user_assigned_identity), whereas an
     app registration would have been a substitute;
  2. it has NO client secret at all, so no credential could leak into an artifact or the repo — the
     token comes from IMDS on the VM the identity is attached to;
  3. it still holds EXACTLY the two authored data roles and nothing else (at9-05 §2).
No superset credential was substituted anywhere.
